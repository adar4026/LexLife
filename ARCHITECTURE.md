# Архитектура приложения «LexLife»

> Личное офлайн-PWA здоровья для одного пользователя.
> Документ синхронизирован с кодом: **схема данных v8**. Источник предметной области — ТЗ «LexLife» (ранее — «Моё Здоровье» / рабочее имя проекта AlexHealth).

---

## 1. Обзор

PWA без фреймворков (чистый HTML/CSS/ES-модули), все данные локально (`localStorage`), офлайн через Service Worker. Интерфейс русский, тёмная/светлая тема. Навигация: нижний таб-бар (4 вкладки) + боковое меню Drawer (☰ справа).

| Аспект | Решение |
|---|---|
| Платформа | PWA, устанавливается «на экран Домой» |
| Код | Чистый HTML / CSS / JS (ES-модули), без сборки и зависимостей |
| Хранение | `localStorage` через единый `StorageService` (async-first) |
| Офлайн | Service Worker, кэш app-shell (`lexlife-v30`) |
| Навигация | Hash-роутер (`#/route`, `#/metric/<key>`, `#/visit/<id>`) |
| Тема | Тёмная/светлая, переключаемая (ключ `app_theme`) |

## 3. Навигация

### Нижний таб-бар (4 вкладки)
```
🏠 Главная  ·  📊 Показатели  ·  💊 Лекарства  ·  🩸 Анализы
```
`TAB_ROUTES = ['home', 'metrics', 'meds', 'tests']`. Кнопка **☰** (правый верх) видна на «основных» экранах (4 вкладки + модули показателей) и открывает Drawer.

### Боковое меню (Drawer, выезжает справа)
```
👤 Профиль (фото, имя, «Нажмите, чтобы изменить»)
──────────────
🔔 Уведомления (•1)   🎯 Цели   📅 Календарь   📈 Статистика
──────────────
🏃 Активность   😴 Сон   💧 Вода   🩺 Врачи и визиты
──────────────
⚙️ Настройки   💾 Резервная копия   🔒 Безопасность   🌙 Тема оформления
```
Любой переход закрывает Drawer (`render()` вызывает `closeDrawer()`).

### Карта маршрутов
```
Вкладки:            home · metrics · meds · tests
Модули показателя:  metric/weight · metric/pressure · metric/pulse · metric/water ·
                     metric/temperature · metric/spo2 · metric/glucose
Визиты (под-экраны): visit/new · visit/<id> · visit/<id>/edit
Анализы (под-экраны): test/new · test/<id> · test/<id>/edit · test-history/<ключ>
Сон:                 sleep · sleep/new · sleep/new/<дата пробуждения> · sleep/<id> (правка) · sleep/settings
Из Drawer:           profile · activity · sleep · visits · calendar · settings · export · theme ·
                     notifications · goals · stats · security
fallback → home
```
Роутер `resolve()`: `metric/water` → модуль воды (`WaterScreen`), прочие `metric/<key>` → `MetricScreen(key)`; `visit/*` → детальный экран / форму визита; под-экраны Drawer подсвечивают вкладку как «не-таб» (☰ скрыта, есть кнопка «‹ Назад»).

## 5. Модели данных

Ключи `localStorage`: все пользовательские входят в бэкап (`DATA_KEYS` → `data`, `app_theme` → `settings.theme`). Не входят: служебный `health_meta` (версия схемы — в заголовке бэкапа) и технические `lexlife_restore_rollback` (временная защитная копия на время restore), `lexlife_last_backup_at` (дата последнего созданного файла).

### 5.1 `health_meta` — служебное
```jsonc
{ "schemaVersion": 8, "seededAt": "2026-06-..." }
```

### 5.2 `health_metrics` — КОНФИГ показателей (цель + единица)
```jsonc
{
  "weight":      { "goal": 75,  "unit": "кг" },
  "pressure":    { "goal": { "systolic": 120, "diastolic": 80 }, "unit": "mmHg" },
  "pulse":       { "goal": 70,  "unit": "уд/мин" },
  "water":       { "goal": 2600, "unit": "мл" },
  "temperature": { "goal": 36.6, "unit": "°C" },
  "spo2":        { "goal": 97,  "unit": "%" },
  "glucose":     { "goal": 5.5, "unit": "ммоль/л" }
}
```

### 5.3 `metrics_log` — ИСТОРИЯ значений всех показателей
```jsonc
{
  "weight":      { "2026-06-20": 82.0 },                          // число (пример)
  "pulse":       { "2026-06-20": 68 },                            // число (пример)
  "temperature": { "2026-06-20": 36.7 },
  "spo2":        { "2026-06-20": 98 },
  "glucose":     { "2026-06-20": 5.2 },
  "pressure":    { "2026-06-20": { "systolic": 118, "diastolic": 76 } },   // объект
  "water":       { "2026-06-20": { "total": 650, "entries": [ { "t": "09:10", "ml": 300 }, { "t": "11:30", "ml": 350 } ] } }
}
```
Значения выше — иллюстративный пример формата, а не реальные данные. У нового пользователя `metrics_log` создаётся пустым (`{}` по каждому показателю) — см. §6.
Тип значения зависит от показателя: число (вес/пульс/темп./сатур./глюкоза), объект `{systolic,diastolic}` (давление), `{total, entries:[{t,ml}]}` (вода — накопительный).

### 5.4 `hydration_cfg` — план гидратации
```jsonc
{ "wakeStart": "07:00", "wakeEnd": "23:00", "slotMinutes": 120, "notify": false }
```
Цель воды берётся из `health_metrics.water.goal` (без дубля). Расписание приёмов **вычисляется** (`buildPlan`), отдельно не хранится.

### 5.5 `app_profile`
```jsonc
{ "name": "", "photo": "data:image/jpeg;base64,..." | null }
```
`name` пустая по умолчанию — пользователь задаёт своё имя сам в экране «Профиль» (боковое меню); на Главной приветствия нет — только дата.

### 5.6 `health_visits` — врачи и визиты (расширено в v7)
```jsonc
[
  {
    "id": "v_a1b2",
    "date": "2026-02-14",
    "doctor": "Dr. Ivanov",
    "specialty": "Терапевт",
    "clinic": "Клиника №1",
    "reason": "Плановый осмотр",
    "conclusion": "Без отклонений.",
    "recommendations": "Повторный визит через год",
    "nextDate": "2027-02-14",
    "status": "done | planned",
    "attachments": [ { "id": "att_1", "kind": "pdf|image", "name": "Заключение.pdf", "mime": "application/pdf", "size": 182734, "blobRef": "att_1", "addedAt": "ISO" } ],
    "links": { "testIds": ["t_0214"], "medIds": ["m_ator"], "reminderIds": [] }
  }
]
```
`links` — задел под связи между модулями: визит ссылается на записи `health_tests`/`health_meds` по `id`; резолвится запросом, без дублирования. `nextDate` — источник строки «Следующий визит» в детали и точки в Календаре.

### 5.7 `notifications` — центр уведомлений (добавлено в v8)
```jsonc
[
  {
    "id": "n_meds1", "type": "meds | water | pressure | weight | tests | visits",
    "enabled": true, "time": "21:00",
    "repeat": "daily | weekdays | weekly | interval | once",
    "days": [1,2,3,4,5],              // для weekly (0=Вс…6=Сб)
    "intervalMinutes": 120, "startTime": "07:00", "endTime": "23:00",  // для interval
    "date": null,                     // для once
    "text": "Пора принять лекарства",
    "ref": {},                        // связь с разделом (medId/visitId/metric/testId)
    "channel": "local",               // "local" | "push" — задел под push
    "lastFiredAt": null
  }
]
```
Одно правило на тип. «Следующее срабатывание» **вычисляется** (`nextFire`/`prevFire` в `services/notifySchedule.js`), не хранится. `lastFiredAt` — последний показанный момент (защита от дублей); при включении/правке правила ставится «сейчас», чтобы прошедшее время не срабатывало задним числом. Доставка сейчас — **только пока приложение открыто на экране** (см. §8.5); поле `channel` и структура готовы к переходу на push без изменения модели.

### 5.9 Активность и лекарства
```jsonc
// activity_days
{ "2026-06-20": { "bike": 50, "bikeIntensity": "Средняя", "steps": 7200, "plank": [45,45], "otherType": "...", "otherMin": 30, "savedAt": "ISO" } }
// activity_goals
{ "bike_minutes": 45, "steps": 8000, "water_liters": 2.3, "plank_seconds": 60 }
// med_log (формат ТЗ) — старый журнал «принял сегодня» по имени; только чтение
{ "2026-06-20": ["Название лекарства"] }
// med_intakes — принятые приёмы по ЛОКАЛЬНОЙ дате (dateKey); одна запись = один приём
{ "2026-06-20": [ { "medId": "...", "scheduledTime": "08:00", "takenAt": "ISO" } ] }   // scheduledTime null — приём без времени
```
Лекарства (`services/meds.js`, чистые функции): без `schedule` действует старое `reminder_time` (одно время, ежедневно) и курс `every_days`; несколько времён = несколько отдельных приёмов в день; «по необходимости» — одна отметка в день, в план дня не входит. `reminder_time` при сохранении формы — зеркало первого времени для старых версий. Снятие отметки удаляет только запись этого приёма этого дня. Правка расписания историю не трогает: принятый приём со старым временем остаётся строкой «вне расписания». «Удалить» — мягкое (`deletedAt`): лекарство уходит из списков, история и связи визитов остаются. Старая отметка `med_log` по имени учитывается, пока у лекарства нет записей `med_intakes` за день, и переносится в приём при первой новой отметке. Уведомления пока общее правило `meds` (§8.5); `medOccurrences(med, day)` — готовая модель «одно срабатывание = один приём» для будущей привязки.

### 5.10 Сон (аддитивные ключи, схема v8 не менялась)
```jsonc
// sleep_log — одна запись на дату пробуждения (основной ночной сон)
[ {
  "id": "mutje19b-1ztl51",
  "date": "2026-10-04",                 // ЛОКАЛЬНЫЙ день пробуждения = дата sleepEnd
  "sleepStart": "2026-10-03T23:40",     // локальное время стены, без UTC
  "sleepEnd": "2026-10-04T07:20",
  "durationMinutes": 460,               // разница настоящих моментов на момент сохранения (CET/CEST учтён)
  "quality": 4,                         // 1–5 или null (не оценено)
  "awakenings": 1,                      // 0–20
  "naps": [ { "minutes": 30, "start": null, "end": null } ],   // дневной сон эпизодами; форма пишет один
  "tags": ["stress", "late_meal"],      // coffee alcohol late_meal stress exercise medication illness screen travel nap
  "note": "",
  "createdAt": "ISO", "updatedAt": "ISO",
  // происхождение — необязательно (задел под внешние источники, см. ниже)
  "source": "manual",                   // "manual" | "apple_health"; нет поля → "manual"
  "externalId": null,                   // id записи во внешнем источнике — дедупликация повторного импорта
  "sourceDevice": null,                 // { "name": "Apple Watch", "manufacturer": "Apple", "model": null } — любой источник
  "importedAt": null,                   // ISO момента импорта
  "sleepStages": {                      // только у внешних записей; у ручных поля нет совсем
    "awakeMinutes": null, "coreMinutes": null, "deepMinutes": null, "remMinutes": null
  }
} ]
// sleep_settings
{ "goalMinutes": 480, "bedtime": "23:30", "wakeTime": "07:30",
  "reminders": { "bedtime": { "enabled": false, "time": "23:00" }, "log": { "enabled": false, "time": "08:00" } } }
```
**Внешние источники (задел, импорта пока нет).** `source`, `externalId`, `sourceDevice`, `importedAt`, `sleepStages` предназначены для будущего импорта сна из внешних источников (Apple Health и другие). Все поля необязательны, миграции нет: запись без `source` (созданная до появления поля) считается `manual` (`sleepSource()`). Новая ручная запись получает `source: "manual"`, `externalId/sourceDevice/importedAt: null`, без `sleepStages`; правка в форме происхождение не меняет. `externalId` не обязателен ни для `manual`, ни для `apple_health`; если он есть, ключ дедупликации — `source:externalId` (`sleepExternalKey`, `findSleepByExternalId`), и `addSleepEntry` отклоняет повтор кодом `DUPLICATE_EXTERNAL`. Проверка копии: `source` — `manual`, `apple_health` или безопасный ключ будущего источника (`^[a-z][a-z0-9_]{0,31}$`); `sourceDevice` — объект со строками `name/manufacturer/model` и простыми лишними полями; `sleepStages` — минуты 0–1440 или null, лишние будущие стадии допустимы. Стадии в интерфейсе и аналитике не используются.

**Apple Health нельзя читать напрямую из текущего PWA:** у веб-приложения в Safari/на экране «Домой» нет доступа к HealthKit. Будущая интеграция потребует iOS/native-компонента (приложение или оболочка с HealthKit permissions), который передаст записи в формате выше.

Схему не поднимали намеренно (как `med_intakes`): новый номер схемы заставил бы старые версии отклонять новые копии; отсутствующие ключи `init()` и восстановление создают по умолчанию (`[]` и настройки выше), старые версии ключи сна в копии игнорируют (whitelist). Ограничения записи: конец позже начала, не больше 20 ч (защита от ошибки даты, не медицинская норма), дата пробуждения не в будущем. Подписи факторов и качества — только в UI (`SLEEP_TAGS`, `SLEEP_QUALITY`), хранятся ключи и числа. CRUD — только `Storage`: `getSleepEntries/getSleepEntry/addSleepEntry/updateSleepEntry/removeSleepEntry`, `getSleepSettings/updateSleepSettings`; повтор даты → `SleepStoreError('DUPLICATE_DATE')`.

### 5.11 Прочее
- `app_theme` (`'dark'|'light'`) — UI-настройка, отдельно от данных; в бэкапе — `settings.theme`.
- `lexlife_stats_period` (`'7d'|'30d'|'3m'|'6m'|'1y'|'all'`) — последний выбранный период «Статистики»; UI-настройка вне `DATA_KEYS`, в бэкап не входит. Статистика не хранится — всегда вычисляется из исходных данных.
- Поле `attachments` на анализах — метаданные документа, сам файл в IndexedDB (§7.2); на визитах — пока каркас (только метаданные).
- **Календарь здоровья не имеет собственной модели** — это агрегатор поверх §5.6/5.8/5.7/5.4 (см. §8.6).

## 6. Миграции (`MIGRATIONS`, последовательно по `schemaVersion`)

| Версия | Что делает |
|---|---|
| **v1 → v2** | Добавлены витальные показатели (`health_metrics`, старый формат со значениями) |
| **v2 → v3** | Добавлена история воды `water_log` (отдельный ключ, литры/день) |
| **v3 → v4** | Обобщение: `water_log → metrics_log.water`; `health_metrics → конфиг`; добавлены temperature/spo2/glucose с тестовой историей; добавлен `app_profile`; старый `water_log` удалён |
| **v4 → v5** | Вода — приёмы по времени: `metrics_log.water[date]` из числа(л) → `{ total(мл), entries:[{t,ml}] }`; конфиг воды переведён в мл |
| **v5 → v6** | Добавлен `hydration_cfg` (план по времени); цель воды 2500 → 2600 мл (только если не менялась пользователем) |
| **v6 → v7** | Расширение визитов: `specialty/clinic/reason/conclusion/recommendations/nextDate/links`; старые поля сохраняются (`desc → conclusion`, `doctor` разбивается на врача+специальность) |
| **v7 → v8** | Добавлен `notifications` — центр уведомлений (по одному правилу на тип), модель сразу под push |

Свежая установка не прогоняет цепочку — `init()` пишет финальное состояние v8 напрямую (`_seed`) с пустыми коллекциями (без демо-истории и без демо-медицинских данных — новый пользователь начинает с чистой базы); существующие данные апгрейдятся `_migrate()` от своей версии до текущей. Генератор детерминированной демо-истории (`genHistory`/`METRIC_SEED`) сохранён только как резерв для миграции v3→v4 очень старых установок и не используется при первичной инициализации.

## 7. Слой данных — `StorageService`

Принципы (зафиксированы ранее, актуальны):
1. **Единая точка доступа** — все экраны только через `Storage`.
2. **Драйвер-адаптер (async-first)** — активен `LocalStorageDriver`; `IndexedDbDriver` — точка расширения (для больших данных и бинарных вложений). Публичный API возвращает `Promise`, экраны используют `await`.
3. **`schemaVersion` + конвейер миграций** (§6).
4. **Резервная копия** — `createBackup/exportBackup` → `parseBackup` → `prepareRestore` → `restoreBackup` (UI на экране «Резервная копия», §7.1).
5. **ISO-даты** — календарные `ГГГГ-ММ-ДД`, метки времени — полный ISO; локализация только в UI.
6. **Вложения** — метаданные в записи; бинарь — через будущий `IndexedDbDriver`.

### 7.1 Резервная копия и восстановление

Формат файла `LexLife-backup-ГГГГ-ММ-ДД-ЧЧММ.json` (не привязан к устройству):
```jsonc
{
  "app": "lexlife",               // принимается также legacy "moe-zdorovie"
  "backupFormatVersion": 2,       // 1 = ранний формат (без поля, дата в exportedAt)
  "appVersion": "1.0.0",
  "schemaVersion": 8,
  "createdAt": "ISO",
  "settings": { "theme": "dark" },
  "data": { /* все DATA_KEYS, включая sleep_log и sleep_settings */ },
  "blobs": {}                     // задел под вложения (§6.6)
}
```
Конвейер (файл — недоверенный ввод):
1. `parseBackup(text)` — только `JSON.parse`, лимит 10 МБ.
2. `prepareRestore(raw)` — **ничего не пишет в базу**: проверка `app`, `backupFormatVersion`, `schemaVersion` (новее текущей → отказ «создана более новой версией LexLife»), `data`; whitelist ключей (неизвестные игнорируются); `__proto__/prototype/constructor` отбрасываются на любой глубине. Затем данные загружаются в песочницу (`MemoryDriver`), старая схема проходит те же `MIGRATIONS` (флаг `noDemoData` — без демо-истории), недостающие разделы получают значения по умолчанию, результат проверяется по структуре схемы v8 (`KEY_VALIDATORS`: типы, даты, время, безопасные id, фото только `data:image/...;base64`). Возвращает сводку для предпросмотра.
3. `restoreBackup(prepared)` — атомарно: снимок текущих ключей → одна защитная копия `lexlife_restore_rollback` (+ в памяти) → запись → перечитывание и `verifyIntegrity()` → успех: копия удаляется; ошибка: откат из снимка. Если приложение закрылось посреди записи, `init()` откатывает при следующем запуске.

Шифрование паролем — будущий формат с полем `encryption` вместо открытого `data`; расшифровка встанет между шагами 1 и 2. Текущая версия такие файлы отклоняет с понятным сообщением.

### 7.2 Документы анализов, полная копия, импорт анализа
Подробно — `docs/FULL_BACKUP.md`. Файлы PDF/фото хранятся в IndexedDB (`lexlife-files` / `attachments`), в `health_tests` — только метаданные; схема данных не менялась (v8), обычная копия — прежний формат 2. «Полная резервная копия с документами» — ZIP: `lexlife-full-backup.json` (манифест) + `backup.json` (обычная копия) + `attachments/<id>.<ext>`. Восстановление: проверка без записи → документы в IndexedDB → атомарная замена данных → удаление непривязанных документов. «Висячие» документы очищаются при запуске (строгое чтение анализов, файлы моложе 10 минут не трогаются). Импорт подготовленного анализа (`kind: lexlife-prepared-test`) добавляет одну запись, повтор блокируется по `importId`; изменения анализов сериализуются (`_serialTests`).

Ключевые методы: показатели (`getMetricsConfig/getMetricConfig/getMetricGoal/setMetricGoal`, `getMetricLog/getMetricLatest/getMetricValue/setMetricValue/addMetricValue`), вода (`getWater/setWater/addWaterEntry/removeWaterEntry/getWaterRecord/getWaterStreak`), гидратация (`getHydration/setHydration`), профиль (`getProfile/setProfile`), визиты (`getVisits/getVisit/addVisit/updateVisit/removeVisit`), уведомления (`getNotifications/updateNotification`), плюс показатели здоровья (alerts/tests/meds), активность, лог лекарств, `createBackup/exportBackup/prepareRestore/restoreBackup/importBackup`, `clearAll`.

## 8. Особые модули

### 8.1 Шаблон показателя
Реестр `METRICS` (UI) описывает каждый показатель (key, name, emoji, unit, kind, шаг). Варианты:
- **`point`** (вес/давление/пульс/температура/сатурация/глюкоза): текущее значение + цель + ввод + история + график неделя/месяц/год + статистика. **Цвет состояния — по норме** (запланировано при их переводе на расширенный шаблон).
- **`cumulative`** (вода): кольцо-заполнение, приёмы суммируются за день.

### 8.2 Модуль «Вода» (`metric/water`) — эталон
Конфиг-движок `WATER_CFG` (`kind:'cumulative'`, пресеты цели/быстрого ввода, `fillColor`). Секции в порядке:
1. Кольцо прогресса (цвет по %: <50 🔴 · 50–80 🟡 · 80–100 🟢 · 100%+ 🔵)
2. Текущий объём / цель (мл)
3. Быстрое добавление (+200/+300/+500 + произвольный)
4. **План гидратации по времени** (фиксированные слоты) — только ориентир: статус порции (выполнено / сейчас / пропущено / впереди) считается по фактическому времени записей (`evaluateWaterPlan`); запись относится к окну своей порции, излишек переносится только вперёд, назад к пропущенным порциям — никогда
5. **Отставание/опережение** + прогноз к концу дня + «догнать план»
6. История приёмов за день (с удалением + подтверждение)
7. Графики **неделя / месяц / год**
8. Статистика: рекорд дня (всё время) · серия дней · среднее нед/мес/год
9. **Настройки напоминаний** (подъём, сон, интервал, тумблер)

### 8.3 Гидратация (Этап 2 — готово; Этап 3 — каркас)
- Пользователь задаёт: суточную цель, время подъёма, время сна, интервал напоминаний.
- `buildPlan(goal, cfg)` — фиксированные слоты от подъёма до сна, объёмы суммируются в цель.
- Каждая ручная запись (`addWaterEntry`) сохраняется с фактическими локальными датой и временем нажатия (один момент для даты и времени); план время записи не меняет. Удаление — по дате показанного дня и совпадению записи (`removeWaterEntry(idx, day, {t, ml})`).
- `plannedByNow()` — целевой накопленный объём к текущему времени (линейно) → отклонение/прогноз/«догнать».
- Напоминания: тумблер на экране «Вода» управляет правилом `water` центра уведомлений (единственный механизм доставки, §8.5); при включении и при смене подъёма/сна/интервала окно и интервал правила берутся из плана. `hydration_cfg.notify` по-прежнему записывается (совместимость бэкапов), но не определяет доставку.
- **Главная** (`homeSummary.js`): текст под шкалой — `homeWaterStatus(current, goal)`, остаток до цели / «Цель выполнена[ · +N мл]» (`waterDayStatus` с допуском ±150 мл этот текст больше не формирует, им пользуется только экран «Вода»). На самой шкале — красная плановая метка, `waterPlanMarker(plannedByNow(...), goal)` → 0…1 (`null` — цели нет, метки нет). Метка обновляется раз в минуту без перерендера экрана: `setInterval` заводится в `renderHomeHero`, гасится при каждом переходе `render()` (включая повторный вход на Главную — не копится). E2E: `tests/e2e/home.e2e.mjs` (дисциплина таймера: не течёт, не дублируется, гасится при уходе).

### 8.4 Модуль «Врачи и визиты» (`visits`)
Заменил read-only «Архив». Список (группы **Запланированные**/**Прошедшие**, «+ Добавить визит») → деталь (`visit/<id>`) → форма (`visit/new`, `visit/<id>/edit`).
- Деталь показывает все поля визита (§5.6), статус-чип, «Следующий визит» (если задан), **связанные анализы и лекарства** (резолвятся по `links.testIds/medIds` в `health_tests`/`health_meds`), вложения (метаданные), Редактировать/Удалить.
- Форма — все поля + мультивыбор связей (чипы, тумблер `is-on`).
- Вложения — только метаданные (имя/тип/размер); реальные файлы — после `IndexedDbDriver`.

### 8.5 Центр уведомлений (`notifications`)
6 типов из `NOTIF_ORDER = ['meds','water','pressure','weight','tests','visits']`, по одному правилу на тип (модель — §5.7). Экран: **панель реального статуса** (поддержка API, разрешение, режим PWA, Service Worker, push-подписка, способ доставки, кнопки «Отправить тестовое уведомление» / «Через 10 с»), карточка на тип с тумблером, сводкой периодичности, текстом и «следующим срабатыванием»; тап по телу карточки раскрывает инлайн-редактор (текст, периодичность — Ежедневно/Будни/Еженедельно(дни)/Каждые N часов(окно, можно через полночь)/Разово(дата), время).
- **Расписание** (`services/notifySchedule.js`): `nextFire`/`prevFire`/`dueFire` — чистые функции, всё в локальном времени устройства (`new Date(y,m,d,h,min)`), без UTC и без зашитой timezone; DST и полночь — движок Date. Тесты — `tests/notifications.test.mjs` в 4 timezone.
- **Доставка** (`services/notifier.js`, `createNotifier`): проверка каждые 30 с (`setInterval`) + `visibilitychange`/`pageshow`; правило с `dueFire` (срабатывание в последние 10 мин, позже `lastFiredAt`) сначала помечается, потом показывается через `registration.showNotification` (данные `route` → клик открывает нужный экран). Параллельные проверки склеиваются — одно срабатывание = одно уведомление.
- **Ограничение платформы (главное)**: это код страницы. Он выполняется, только пока LexLife открыт на экране. Свёрнутое приложение, заблокированный экран, закрытое PWA — iOS замораживает/выгружает страницу, таймер не идёт, напоминание не приходит (при возврате в течение 10 мин — покажется с опозданием). В Safari нет Notification Triggers и Periodic Background Sync — локально «разбудить» приложение в нужное время нечем. Экран статуса говорит об этом прямо.
- **Фоновая доставка (Web Push, Cloudflare)** — подробно в `docs/CLOUDFLARE.md`. `services/pushClient.js`: устройство (UUID + токен, вне бэкапа), `pushManager.subscribe({ userVisibleOnly: true })`, зеркало расписания на сервере (без текстов) с синхронизацией по «отпечатку» (offline, restore, смена timezone). Сервер (`worker/`, D1, cron раз в минуту) шлёт push; `sw.js` показывает его с `tag = occurrenceId` и пишет occurrence в Cache API (`services/occurrenceStore.js`). Локальный планировщик не показывает то, что пришло push'ем, а пока push основной — ждёт его 2 мин (запасной показ). На GitHub Pages `/api` нет — экран честно пишет «нет на этом адресе», работает только локальная доставка.
- **Экран статуса**: системное разрешение, Service Worker, push-подписка, сервер уведомлений, фоновая доставка, последняя синхронизация, последний серверный push; кнопки «Проверить локальное уведомление», «Проверить фоновый push», «Включить/Отключить фоновые уведомления».

### 8.6 Календарь здоровья (`calendar`)
**Агрегатор без собственной модели данных** — читает `health_visits`, `health_tests`, `health_meds` (+ вычисляемая следующая доза `nextDose`), `notifications`, `health_metrics.water.goal`. Режимы: **Месяц** (сетка Пн-первая, точки на днях с разовыми событиями), **Неделя** (7-дневная полоса), **Список** (ближайшие 60 дней, только дни с разовыми событиями).
- **Точки на сетке** — только для разовых событий: дата визита, `nextDate` визита, дата анализа, вычисленная следующая доза лекарства (`every_days`), уведомление с `repeat:'once'` (`dayPointEvents`/`dayHasDot`). Ежедневные события (лекарства с `reminder_time`, ежедневная цель воды) **не** создают точку.
- **Панель дня** (под сеткой Месяц/Неделя) — полная повестка: точечные события + ежедневные (`dayAgendaEvents`), отсортированные по времени.
- Тап по событию открывает связанный объект: визит → `visit/<id>`, анализ → `tests`, лекарство → `meds`, уведомление → `notifications`, цель воды → `metric/water`, сон → `sleep/<id>`.
- **Сон** — в панели дня пробуждения «😴 Сон · 7 ч 28 мин» (строится из `sleep_log` при открытии, событий не хранит); точку на сетке, как и прочие ежедневные записи, не ставит.

### 8.7 Статистика (`stats`)
Экран только рисует готовую модель; все расчёты — чистые функции `services/analytics.js` (без DOM/Storage, вход не изменяется). `createStatsEngine(raw, today)` один раз извлекает ряды, `forPeriod(key)` мемоизирован.
- **Ряды**: `metrics_log` → `[{date, day, value, n}]`. Точечные показатели — только положительные числа; давление — отдельно SYS/DIA; вода — `total` записи дня (реальный 0 учитывается, отсутствие записи — «нет данных»); активность — минуты (вело + другое + планка/60) и шаги отдельно. Несколько значений за день (массив) → среднее за день, `n` — число измерений. Будущие даты не учитываются.
- **Периоды**: 7/30/90/180/365 дней, заканчиваются сегодня; «Всё время» — от первой записи. Предыдущий период — соседний той же длины (для «Всё время» нет).
- **Тренд**: МНК-регрессия по дневным значениям; нужен минимум 5 дней с данными на отрезке ≥ 5 дней. Направление объявляется, только если |наклон × отрезок| ≥ порога заметности (`MIN_DELTA`) и |t| ≥ 2; иначе «выраженного изменения не видно».
- **Цели**: вес — из `health_metrics` (пунктир на графике); давление — только явно сохранённая пользователем цель (`isUserGoal`: запись с собственной меткой `at` от `setMetricGoal`, а не из пакета значений по умолчанию), иначе линии/плитки цели нет; вода — % дней с записями, где цель достигнута, серии (день без записи прерывает серию); активность — `activity_goals` (вело, шаги).
- **Графики** (`ui/charts.js`, без библиотек): ось X пропорциональна датам, все точки сохраняются; для 3+ месяцев столбцы агрегируются по неделям/30 дням (среднее по дням с записями). Тап — карточка значения; `touch-action: pan-y` — вертикальный жест остаётся прокруткой.
- **Медицинская безопасность**: только факты и математические тренды, нейтральные формулировки; «вне справочного диапазона» — только для анализов (`REFERENCE`).

### 8.8 Журнал анализов и «Документ анализа» (`tests`, `test/*`)
- **Порядок.** `Storage.getTests()` → `sortTests`: даты по убыванию, в одну дату — позже добавленный выше (порядок хранения = порядок добавления; схема не менялась). `journal()` только устойчиво сортирует по дате, поэтому повторный вызов порядок не меняет. Несколько записей в одну дату — отдельные строки «Анализ № 1 / № 2».
- **Строка журнала.** Дата («14 февр. 2026 г.»), группы бланка (`groupSummary`: группы лаборатории + разделы основных полей, которые бланк не покрывает), блок документа (тип · имя · размер) или «Без документа», ›. Тап по строке → `test/<id>`; тап по блоку документа → просмотр документа (адрес не меняется).
- **Полный анализ.** Разделы (`testSections`): основные поля по фиксированной карте, показатели лаборатории — по названию (рус./лат./исп.), затем по группе бланка, иначе «Другие показатели»; группы «Анализ мочи» и «Кал» — всегда свои разделы (текстовые результаты как на бланке, без графика). Отметка: точка — справочные значения приложения (основные поля), ↑/↓ — вне диапазона лаборатории. Ключ истории: имя поля, `urine_*` для стандартных показателей мочи (`urine_ph`, `urine_specific_gravity`, `urine_protein`, `urine_glucose`, `urine_nitrites`, `urine_ketones`, `urine_urobilinogen`, `urine_bilirubin`, `urine_hemoglobin_myoglobin`, `urine_sediment` — определяются по названию в группе мочи, на экране — единое название, исходное показано «на бланке: …»; в записи название не меняется) или `c:<название без регистра>`.
- **Прокрутка.** Место прокрутки хранится в `history.state.y` (сохраняется по окончании прокрутки и перед каждым тапом); экраны с `restoreScroll` при возврате «Назад» открываются на прежнем месте, при новом переходе — сверху.
- **Просмотр документа** (`js/ui/docViewer.js`). PDF — локальный pdf.js (`js/vendor/pdfjs`, legacy-сборка, worker — модуль), все страницы вертикально, счётчик «N / M», масштаб 100–400 % (−/+, щипок, двойной тап); рисуются только страницы рядом с экраном (canvas ≤ ~5 Мпикс, DPR ≤ 2), далёкие освобождаются. Фото — полноэкранно, масштаб до 600 %, перетаскивание. «Поделиться» — `navigator.share({ files })` синхронно из касания; без поддержки — «Сохранить». «Открыть отдельно» — Blob URL в новом окне. Ошибка встроенного просмотра — сообщение и те же кнопки. `DocSession` владеет Blob URL, pdf.js-документом/worker, canvas, наблюдателями и обработчиками; закрытие (кнопка, Esc, «Назад»/смена адреса) освобождает всё.
- **Тесты.** `tests/tests-journal.test.mjs` (node, синтетические данные); `tests/e2e/tests-journal.e2e.mjs` — сквозной сценарий в браузере, запускается только на localhost и возвращает данные origin после себя.

### 8.9 Сон (`sleep`) — `services/sleep.js`
Все расчёты — чистые функции без DOM (тесты `tests/sleep.test.mjs` в Мадриде, Лос-Анджелесе, Токио и UTC):
- **Время и дата:** `calculateDuration` (между `Date` локального времени, не «ЧЧ:ММ»), `inferBedDate` (23:40 → накануне, 00:30 → тот же день), `sleepDateFor` (день пробуждения), `formatSleepDuration/formatSleepDelta`.
- **Пропуски — не ноль:** все средние только по записанным ночам; дневной слот без записи — `null`.
- `averageSleep`, `averageQuality`; `averageBedtime/averageWakeTime` — циклическое среднее по кругу суток (23:50 и 00:10 → 00:00).
- `sleepConsistency` — «Стабильность режима», %: среднее отклонение времени отхода ко сну и подъёма от обычного (по кругу суток); 0 мин → 100 %, ≥ 2 ч → 0 %, меньше 3 записей → нет значения.
- `sleepGoalRate` (среди дней с записью), `currentSleepStreak` (дни подряд с ночным сном ≥ цели по сегодня; сегодня не записано — по вчера; пропуск прерывает), `bestSleepStreak`.
- Периоды календарные: `periodBounds/shiftPeriod` (неделя Пн–Вс, месяц, год); `aggregateByWeek/aggregateByMonth` (дни), `aggregateByYear` (средние по месяцам); `comparePeriods` (нет данных в одном из периодов → нет сравнения).
- `factorInsights` — «Что связано с вашим сном»: разница средней длительности (≥ 15 мин) или качества (≥ 0,3) в днях с фактором и без; только при ≥ 5 днях с фактором и ≥ 5 без; формулировки без причинности (`insightText`).
- Поля происхождения и `sleepStages` на аналитику не влияют (тест «аналитика не зависит от источника и стадий»).
- Основной показатель — ночной сон; дневной сон и «общий сон за сутки» (`totalDayMinutes`) показываются отдельно и подписаны.
- **Напоминания** (`SLEEP_REMINDERS`: `sleep_bedtime` «Пора готовиться ко сну», `sleep_log` «Записать сон»): модель в `sleep_settings.reminders` и `sleepReminderRules()` в формате правил центра уведомлений. В ключ `notifications` пока не добавляются: сервер фоновых уведомлений (`worker/rules.js`, `RULE_TYPES`) отклоняет неизвестные типы, и синхронизация всех правил сломалась бы. Подключение — отдельный этап вместе с сервером.
- Графики — `ui/charts.js` (необязательные параметры `xLabels`, `yFormat`, `yStep`, `domain`, `barColor`, `fit`); столбцы «меньше цели» — тот же оттенок слабее (`--sleep-below`), состояние также написано в карточке значения.
- Главная: секция «Сон» под hero (запись за сегодня или «Сегодня нет записи · Добавить», → `sleep`). E2E: `tests/e2e/sleep.e2e.mjs`.

## 9. Тема, профиль, офлайн
- **Тема** — `app_theme` в `localStorage`, `applyTheme()` ставит `data-theme` на `<html>`; светлая палитра в `[data-theme="light"]`.
- **Профиль** — имя + аватар (фото сжимается в 200×200 JPEG, хранится data-URL).
- **Service Worker** `lexlife-v35` — предкэш оболочки (запросы предкэша с `cache: 'reload'`, мимо HTTP-кэша) (HTML/CSS/JS/manifest/иконка) + кэш Google Fonts (stale-while-revalidate) + обработчики `notificationclick` (открытие нужного экрана) и `push` (Web Push сервера LexLife, журнал occurrence `lexlife-occ-v1`). Запросы `<scope>api/*` не кэшируются. Обновление ассетов — инкремент `CACHE_VERSION`.

## 10. Развёртывание (GitHub Pages; Cloudflare — параллельно, см. `docs/CLOUDFLARE.md`)

Приложение — статический сайт без сборки, поэтому подходит для GitHub Pages «как есть»:
- Все пути (CSS/JS/manifest/иконки) относительные, без ведущего `/` — работает и из корня, и из подкаталога `https://<user>.github.io/<repo>/`.
- `manifest.json`: `start_url: "./index.html"`, `scope: "./"` — относительные.
- SW регистрируется как `navigator.serviceWorker.register('sw.js')` (без ведущего `/`) — scope автоматически совпадает с каталогом сайта.
- Роутинг — hash-based (`#/route`), сервер не участвует в маршрутизации, обновление страницы не ломает навигацию.
- Тот же код без изменений отдаётся Cloudflare Worker'ом от корня `/` (`dist/` собирается allowlist'ом `scripts/build-assets.mjs`; `worker/`, `tests/`, `private/` туда не попадают).
- `.nojekyll` в корне отключает обработку Jekyll на GitHub Pages (не нужна для чистого статического сайта).
- Новый пользователь (в т.ч. первый запуск на iPhone) получает пустую базу — см. §6, §12 «Приватность».

### Приватность и seed-данные
До ревизии, синхронизированной с этим документом, `_seed()` заполнял базу реальными медицинскими данными как «демо». Начиная с этой ревизии — все пользовательские коллекции (`health_alerts`, `health_tests`, `health_meds`, `health_visits`, `metrics_log`) инициализируются пустыми; `app_profile.name` — пустая строка; конфиги показателей — нейтральные системные значения. Экспорт/импорт бэкапа (`exportBackup`/`importBackup`) — единственный предусмотренный способ перенести реальные данные с одного устройства/браузера на другое (например, с Mac на iPhone) без появления их в исходном коде.
